## Commands

```bash
npm run dev      # dev server (http://localhost:3000)
npm run build    # production build — also the only full type-check (tsconfig is noEmit)
npm run lint     # eslint (flat config, eslint-config-next core-web-vitals + typescript)
npm start        # serve the production build
```

There is no test framework configured — no test runner, no test files, no `test` script.

`./scripts/create-supabase-user.ps1 -Email x@y.com -Password "..."` bootstraps the first user
via the GoTrue signup endpoint, reading URL/anon key from `.env.local`. It does not set
`role` or `company_name`, so a user created this way is a `visualizador` invisible to the
admin RPCs until those metadata keys are set by hand in Supabase Studio.

`./scripts/create-supabase-user-prod.ps1 -Email x@y.com` is the one to use against production:
it calls the GoTrue Admin API with the service key from `.env.prod` (base URL + secret key of
the prod project), confirms the e-mail and writes `full_name`, `role` (default `admin`) and
`company_name` like `app/usuarios/actions.ts` does. It sends its own `User-Agent` because the
Supabase gateway rejects `sb_secret_` keys from anything that looks like a browser, and
PowerShell 5.1's default agent starts with `Mozilla/5.0`.

### Migrations

SQL lives in `supabase/migrations/` and is applied by **GitHub Actions**, never by hand:
a push to `dev` runs `supabase db push` against the development project, a merge to `main`
runs it against production (`.github/workflows/supabase-{dev,prod}.yml`). The two projects are
in **different Supabase accounts**, so each GitHub Environment (`Preview` for dev, `Production`
for prod — named to match Vercel's scopes, and the `environment:` key in each workflow must
match exactly) carries its own
`SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_ID` and `SUPABASE_DB_PASSWORD`. There is no
repo-level token on purpose — one would let a job authenticate as the wrong account.

Create a change with `npx supabase migration new nome`; the timestamp in the filename is the
order. Files are **forward-only** — the CLI never runs a down section — but the existing ones
keep their `-- UP --` / commented `-- DOWN --` shape, and new ones should too, since the DOWN
block is the documentation of how to undo a step by hand. End anything that changes the schema
or a function signature with `NOTIFY pgrst, 'reload schema';` so PostgREST picks it up.

Two rules that come from how this repo was migrated into the CLI, both worth keeping:

- **Never write a destructive statement into a migration.** The original `schema.sql` opened
  with `DROP TABLE clientes`; that block was removed when it became
  `supabase/migrations/20260901000000_schema_inicial.sql`, because these files now run
  unattended against databases holding the agency's real clients.
- **Seed data for lookup tables belongs in the migration that creates them** (see the
  `aeroportos` / `destinos` inserts in `…_proposta_dados.sql`, written `ON CONFLICT DO NOTHING`).
  `supabase/seed.sql` only runs on a local `db reset`, so anything a remote project needs has
  to be a migration.

Docker is only needed for local CLI work (`db pull`, `db diff`, `supabase start`) — the CI jobs
talk straight to the remote database without it.

### Environment

`.env.local` holds `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
`SUPABASE_SERVICE_ROLE_KEY` (server-only) and `N8N_TEMPLATES_WEBHOOK_URL`. The n8n variable
is not read by any code yet — see "Not wired up yet" below.

## What this app is

An internal tool for a travel agency (ThaMu Viajando). Agents track clients through a sales
funnel, build one or more *cenários* (trip scenarios: a hotel plus flights, ground transport
and tours) per client, and then render a printable proposal by overlaying live data onto a
page image exported from Canva. Everything is in Portuguese — routes, DB columns, identifiers
and comments. Keep writing it that way; only Claude-facing docs like this one are in English.

## Architecture

### Next.js 16 conventions in use

Read `node_modules/next/dist/docs/` before writing routing/caching code; several conventions
here differ from older Next.js:

- **`proxy.ts` at the repo root is the former `middleware.ts`.** It exports `proxy()` and a
  `config.matcher`. Its only job is calling `supabase.auth.getClaims()` so the session cookie
  is refreshed on every request — Server Components cannot write cookies, so removing it
  silently expires sessions early.
- `params` and `searchParams` are Promises and must be awaited.
- `PageProps<"/route">` and `LayoutProps<"/">` are globals generated by Next; pages use them
  instead of hand-written prop types (some pages still spell the props out inline — both
  appear in the codebase).

### Supabase: three clients, do not mix them

| File | Use from | Key |
| --- | --- | --- |
| `lib/supabase/server.ts` | Server Components, Server Actions | anon + cookies |
| `lib/supabase/client.ts` | `"use client"` components | anon |
| `lib/supabase/admin.ts` | Server Actions only | **service_role** |

`admin.ts` bypasses RLS; importing it from a Client Component would ship the secret to the
browser. It is currently used in exactly one place: creating users in
[app/usuarios/actions.ts](app/usuarios/actions.ts).

### Auth and roles

There is no profiles table. Identity lives in `auth.users.raw_user_meta_data`:
`full_name`, `role` (`admin` | `visualizador`, defaulting to `visualizador`) and
`company_name` (must equal `thamu_viajando`; the DB is shared with other projects).

Every page repeats the same opening: `createClient()` → `auth.getClaims()` →
`redirect("/login")` when there are no claims → `supabase.rpc("thamu_viajando_is_admin")` →
pass `email`, `name`, `isAdmin` to `<AppHeader>`, which hides admin-only nav items. Server
Actions repeat their own guard (`requireSession()` / `getAdminSession()` helpers, defined
locally per actions file).

User management goes through `SECURITY DEFINER` functions (`migrations/auth/`), not direct
table access: `thamu_viajando_admin_list_users / _confirm_user / _update_user / _delete_user`.
Each re-checks `thamu_viajando_is_admin()` **inside the function**, filters by
`company_name`, and blocks changing your own role or deleting yourself. When changing what an
admin may do, change the SQL function — the TypeScript check is only a UX shortcut.

Table RLS (`migrations/tables/`) is deliberately coarser: `anon` is revoked everywhere, and
any *authenticated* user gets full read/write on `clientes`, `cenarios`, `voos`, `transporte`,
`passeios`, `proposta_templates` and `proposta_valores`. The `visualizador` role is **not**
enforced at the row level — it only hides UI. Don't assume the DB will stop a non-admin write.

### Data model

`clientes` 1—N `cenarios` 1—N (`voos` | `transporte` | `passeios`). A cenário carries its
single hotel inline as `hotel_*` columns. Money totals (`hotel_valor_total`, `voos.total`,
`transporte.total`, `passeios.valor_total`) are **generated stored columns** — never write
them; write the unit price and quantity.

Proposals add two tables: `proposta_templates` (page image URLs + a `campos` JSONB layout)
and `proposta_valores` (hand-typed values, unique per `cenario_id` + `template_id`).

`proposta_dados` (`migrations/tables/012`) is a **view**, one row per cenário, that turns those
rows into the exact strings the Canva artwork shows: `"6 DIAS & 5 NOITES"`, `"5 diárias"`,
`"1 escala (BSB 7h40)"`, `"R$ 1.930"`. It also returns `voos`, `transfers` and `passeios` as JSONB
arrays of already-formatted items. It is `security_invoker = true`, so it respects the caller's RLS.
Items whose `status` is `Opção` or `Cancelado` are left out of both the lists and the cost
(`thamu_viajando_item_valido`). Prices come from `cenarios.markup_percentual` (cost per person
× markup, rounded up to R$ 50; pix applies `desconto_pix_percentual` and rounds down to R$ 10);
with no markup the value columns are null. Two lookup tables feed it: `aeroportos` (IATA → city,
for "Origem: Curitiba") and `destinos` (**hotel city** → state, because the airport is often in
another city — "Pipa" is not Natal). Missing entries degrade to the raw code / an empty state;
add rows by hand. Prefer adding a column to the view over formatting in TypeScript.

The `*-import.csv` / `*-import.sql` files at the repo root are one-off seed data from the
agency's spreadsheets, not part of the build.

### The proposal renderer

[lib/proposta/template.ts](lib/proposta/template.ts) is the contract everything else agrees
on — read it first when touching proposals.

- A template is a list of page images plus `campos: Campo[]`. Each campo is either a
  `CampoTexto` (a dotted path into `{cliente, cenario, totais, proposta}`, e.g. `cenario.destino`
  or `proposta.duracao`) or a `CampoLista` (`fonte: voos|transporte|passeios`, or
  `proposta.voos|proposta.transfers|proposta.passeios` for the pre-formatted ones) rendered
  through a `linha` mini-template like `"{cia} · {origem} → {destino} · {total:moeda}"`.
- The `proposta` group is one row of the `proposta_dados` view, loaded by
  `carregarDadosProposta()` in [lib/proposta/dados.ts](lib/proposta/dados.ts), which both
  `/proposta/[cenarioId]` and the editor at `/templates/[id]` use.
- **The editor only offers `proposta.*`**: `caminhosDisponiveis()` lists the view's scalar
  columns and `FONTES` its three JSONB arrays, so a new value on a template means a new column
  in the view, not formatting in TypeScript. The renderer still resolves `cliente.*`,
  `cenario.*` and `totais.*` for templates saved before that, and `comAtual()` keeps such a
  path in the dropdown so opening an old field doesn't silently repoint it.
- **All geometry is percentages of the page**, and `fontSize` is in `cqw` (% of the page
  container's width), so a proposal renders identically on screen, in the editor and in print
  at any size. `@page` size comes from the template's `largura_mm`/`altura_mm`.
- `origem` decides where a value comes from: `dado` (read from the DB), `manual` (typed in the
  wizard, stored in `proposta_valores`) or `ia` (reserved, see below). Only `manual` text
  fields are editable in the wizard — `camposManuais()` is the single source of truth for that.
- `chaveDoCampo()` / `chavePadrao()` produce the stable key used both as the storage key in
  `proposta_valores.valores` and as the form field name. `salvarCampos` enforces uniqueness by
  suffixing duplicates; renaming a key orphans previously saved values.
- [app/components/proposta-documento.tsx](app/components/proposta-documento.tsx) renders a
  proposal. Passing it an optional `editor` prop turns the same component into the
  drag/resize/rotate canvas used by [app/components/editor-campos.tsx](app/components/editor-campos.tsx)
  — one renderer, two modes, so the editor cannot drift from the printed output.

Flow: `/templates` (CRUD + upload) → `/templates/[id]` (position fields over a real cenário) →
`/criar-proposta` (pick cliente → cenário → template, fill manual fields) → `gerarProposta`
upserts `proposta_valores` → `/proposta/[cenarioId]?template=N` renders and prints.

### Storage and uploads

Template page images live in the public `propostas` bucket under `templates/`. Uploads go
**directly from the browser** to Supabase Storage ([templates-manager.tsx](app/templates/templates-manager.tsx))
because Server Actions cap request bodies at 1 MB; the Server Action then only accepts URLs
whose origin is the project's Supabase host and whose path starts with the expected bucket
prefix (`paginaValida` in [app/templates/actions.ts](app/templates/actions.ts)). Keep that
validation if you touch the upload path. The bucket is public on purpose — the images are
artwork, and `<img>` in the printed document must load them without a token.

### Conventions

- **Server Actions** return `{ error?: string; success?: string } | undefined` and are driven
  from the client with `useActionState`; forms show the result through `<FormFeedback>`.
  Actions sanitize every field themselves (`text()`, `numero()`, `integer()`, `decimal()`
  helpers redefined per file) and call `revalidatePath` for each affected route.
- **UI primitives** live in [app/components/ui/](app/components/ui/) (`Button`/`buttonClass`,
  `Card`/`PageHeader`/`EmptyState`, `Input`/`Select`/`Field`/`FormFeedback`, `Badge`, table
  parts) and compose class strings with `cn()` from [lib/cn.ts](lib/cn.ts). Use them rather
  than restyling elements inline.
- **Design tokens** are defined once in [app/globals.css](app/globals.css) — brand colors,
  surfaces, shadows, easings and animations under Tailwind v4 `@theme`, plus custom utilities
  (`app-canvas`, `airmail` — the red/blue airmail-envelope stripe used by the header and login — and `skeleton`). Headings use Gabarito (`font-display`), body text Hanken Grotesk. There is no `tailwind.config`; theme changes go in
  that file. Dates are formatted by slicing the `YYYY-MM-DD` string, never through `Date`,
  to avoid timezone shifts on `DATE` columns.
- PostgREST query builders are consumed when awaited — [app/clientes/page.tsx](app/clientes/page.tsx)
  rebuilds filters per query for that reason. User input going into `.or()` must pass through
  `escapeFilterValue`.
